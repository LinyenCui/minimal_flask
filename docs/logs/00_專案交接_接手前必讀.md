## 1. 部署／分支鐵則（最常踩）

- **Render 部署來源 = `origin/main`**。「上線」= 進 main。
- 開發在 `dev_line_channel`。推 main 用 refspec：`git push origin dev_line_channel:main`
  （非 force、不 checkout main）。
- **commit 精準 `git add <檔>`，絕不 `git add -A`** —— repo 有大量 `db_backups/`、
  `reference_data/`、未進版控的 WIP。
- **推 main 前 pre-flight**：`git fetch` → `git log --oneline origin/main..dev_line_channel`
  → 掃紅線（`AIzaSy` / `password=` / `DROP TABLE` / service-account json）。
  ⚠️ **Codex 共用這個 repo，dev 上可能有你不知道的 commit** ——
  2026-08-17 推 main 時就順帶把 Codex 的處方 OCR（`a7078121`）一起推上去了。
  推之前一定要看清單，不是只看自己的 commit。
- 本地 DB 與 Render DB **完全獨立**。要上 Render 的 DDL 給使用者用 Adminer 手動跑。
- 本地測試：`python app.py`（port 3000）+ `ngrok http 3000`；**改 .py/.env 要重啟才生效**。
- **LIFF 的改動只有推 main 才驗得到** —— LIFF App 的 Endpoint 寫死指向
  `minimal-flask.onrender.com`，本地 ngrok 開不到。前端改動別浪費時間在 dev 上驗。
  部署後 LINE 內建瀏覽器快取很兇，要**整個關掉視窗再重開**，不是下拉重整。

## 2. 核心設計：三時間態（不懂這個什麼都會做錯）

| 時間態 | 資料表 | 概念 |
|---|---|---|
| 未來態 | `fixed_schedules` | 模板，尚未匯入 |
| 現在態 | `trips` | 生產線上的班次 |
| 過去態 | `completed_trips` | 已完成 |

**業務週 = 太陽週（星期日～星期六）**，用 `strftime('%U')`，helper 在
`rewrite/utils/sun_week.py`。**不可以用 ISO 週**（會差一天）。
⚠️ 但 `trips.week_number` 這個欄位存的是 **ISO 週**（`isocalendar()`，
`import_fixed.py` 寫入時就這樣）—— 兩者不同，別互相「修正」。

## 3. 政策與判準（**這一節最重要 —— git log 查不到**）

這些是使用者在對話中定下的，沒寫在程式裡就會被下一輪推翻。

### 3.1 「請假」不等於「沒跑」
三層障眼法的請假是「**同車某位乘客沒來，車照跑**」：

```
乘客欄「（廖貴7:30）→寶珠7:40 →診所7:45」
        ^^^^^^^^^ 括號=這位請假，但寶珠照載
→ 錶價 200 照跳、加成 −95 只扣廖貴那份，司機實拿 105
```

PROD 全部 151 筆請假班次錶價**都 > 0**（85~450），沒有任何一筆是 0。
2026-08-05 因為誤解成「司機沒跑」而把請假班次排除在司機車資之外，
少算了 12,315 元。**任何「請假 → 排除」的邏輯先回來讀這段。**

### 3.2 修改原因政策
- **只有改金額才需要問原因。** 改日期、換司機、撤銷指派 → 確認卡就是防呆，不問原因。
- **不影響金額的修改不可以寫進 `modification_reason`** —— 請款報表讀那一欄
  （`report_service.py:635-650` 讀 `modification_reason` 與 `passenger_leave_reason`），
  寫進去會污染說明欄。
- `trips.modification_reason` 會被 scheduler **原封複製**進 `completed_trips`
  （`scheduler_service.py:240-260`），所以現在態寫進去照樣會進報表。
- 過去態要留原因就寫 **`completed_trips.remarks`** —— 報表不讀那一欄。
- 現在態沒有備註欄，軌跡只放 `audit_log`。

### 3.3 前綴政策
- 藥：`/藥名`、`/drug`；診斷：`/dx`、`/碼`。**裸字一律不收**（「藥」曾誤觸群聊）。
- `!` + 日期 = 回診日期計算，**專用**。
- 群組訊息必須 `/` 開頭才會被處理（例外：多輪對話 state）。
  ⚠️ 給 Quick Reply 的 `text` 若是新的確認詞，**群組裡會被閘門靜默丟棄** ——
  除非那個詞在 `sandbox_handler._QUICK_COMMAND_PREFIXES` 白名單裡，
  或 text 本身帶 `/`。2026-08-05 的「確認執行」按鈕就是這樣變死鍵的。

### 3.4 本地 ↔ Render 同步：鏡射窗口

同步要同時滿足兩件看似互斥的事（2026-08-24 定調）：
  · 本地是拿來測試的 → Render 還有資料的期間，本地就該**等於** Render
  · 用戶會定期刪掉 Render 三～六個月前的資料瘦身 → 那些歷史**只剩本地有**，
    不能因為「Render 沒有」就被當垃圾刪掉

用時間切開，不需要任何設定：

```
鏡射窗口 = Render 現存資料的最早日期 MIN(date) 之後
  · 窗口內：Render 是唯一真相 —— 本地獨有的刪掉、內容不同的用 Render 刷新
  · 窗口外（更舊）：本地的歷史保存庫 —— 一律不動
```

會自己維護：Render 一瘦身，MIN(date) 往前移，本地那批舊資料自動落到窗口外
受保護。判定在 `scripts/sync_from_render.py::classify_local_completed_row`
（純函數，`scripts/test_sync_mirror_window.py` 有測）。

⚠️ 之前的坑：同步曾是「只增不改」（路徑 2 只挑 `code not in local_codes`），
於是在 Render 上改過的班次永遠傳不到本地，累積 151 筆分岔，
使用者因此以為程式改壞了。現在有步驟 2b `refresh_existing_completed_from_render`。

⚠️ 「序號衝突」是誤報：本地的 Flask 排程也會把班次掉進 completed_trips，
本地 max_id 本來就會跑在 Render 前面。腳本早就會自動處理，
所以 UI 不該因此把按鈕換成「⚡ 強制同步」（曾經每次同步都逼人按）。

### 3.5 推播額度
免費 200 則/月，**reply 不計、push 才計**。
- LIFF 完成後的通知走 **chat_text 協議**：前端 `liff.sendMessages()` 發送 → **0 額度**。
  只有在 LINE 外面用瀏覽器開才 fallback 成真 push。
- 批次操作：逐筆 POST 帶 `suppress_push=true`，收尾彙總一則 → N 筆 = 0~1 則。
- **打自己 server 的 POST 不吃額度**（使用者問過）。
- 指令 `推播用量` 查本月各來源用了幾則（`modules/utils/push_stats.py`）。

### 3.6 AI 行為不如預期時
**不要寫 deterministic regex 繞過 AI。** 改 schema description / skill prompt /
atomic tool docstring。2026-08-05 「固定班表 安北05」查不到，根因是
`route_number` 在查詢 schema 裡沒有描述（它其實是「週幾組合」不是路線編號），
補上描述就好了。

## 4. 陷阱地圖（踩過的坑，別再踩）

### 4.1 `unique_code` 是身分證，而且**日期編在裡面**
```
預約 temp   T_{trip_id}_{YYYYMMDD}
固定 fixed  {fixed_id}_{day_of_year}_{ISO週}
```
它是兩件事的比對主鍵：scheduler 把班次掉進 `completed_trips`
（`ON CONFLICT (unique_code) DO NOTHING`）、Render↔本地同步（`DO UPDATE`）。

**只改 `date` 不改 `unique_code`** → 那筆帶著說謊的身分證掉進過去態 →
之後重匯同一週會產出同 code 的新班次 → 撞 `DO NOTHING` **靜默丟掉一筆**，
車資消失且沒有錯誤訊息。全庫只有一個 trigger（`customers.updated_at`），
資料庫不會幫你補。改日期請用 `update_trip_date` / `update_completed_trip_date`。
重算邏輯在 `rewrite/tools/trip_identity.py`。

### 4.2 `0` 是 falsy —— 金額判斷的頭號殺手
踩過四次：
- `if surcharge:` → 0 元請假的通知連金額那行都不印，操作者看到「完全正常」的訊息
- `v is None: continue` → AI 漏傳金額時確認卡不顯示「加成」列
- `if ct.computed_total:` → 沖帳班次（140/−140=0）在已完成列表顯示「未記錄」
- `aggregate` 自己寫的「總額 > 0」→ 同一筆在列表顯示 0、在統計卡卻算「未記錄」

**「這筆車資填過沒」的判定收在 `rewrite/tools/fare_rules.py`**（Python + SQL 兩種形式），
**五個**使用者共用：列表顯示、View 的 has_fare、統計卡 aggregate、查詢過濾、
司機待補清單。規則：**填過 = 錶價≠0 或 加成≠0 或 備註有「改車資」**。
再有第六個地方要判斷，**去引用它**——`test_driver_fare_rules.py` 有一條
全 repo 掃描會抓到新長出來的自訂判定。

### 4.3 途經欄的分隔符有兩種
`via_point` 的多段用 `+` 或 `→` 都有（歷史寫法並存）。查詢一律用
`regexp_split_to_array(via_point, '\s*[+→]\s*')`。
⚠️ 但 `passenger_name` 裡的 `+` 是「同一站多帶一人」（`宗輝+外傭`），語意不同，
別套同一套 parser。

### 4.4 iOS LIFF WebView 同頁多次 fetch 會掉
實測 `Promise.all` 與 sequential 都會在 client 端掉、server 連 GET 都收不到。
所以批次表單**只打一支** `GET /liff/trips/batch`（班次＋司機清單一起回）。
要加新資料就搭這支，**不要另外開 fetch**。

### 4.5 30 分鐘鎖不是每個動作都鎖
`assign_driver` / `unassign_driver` / `record_fare_current` / `update_passenger_name`
是 `allow_in_lock=True`（快到點了才更需要派車）。狀態變更類才是嚴格鎖。
批次表單的「將執行 N/M 筆」判定要跟著分，照抄會顯示錯的筆數。

### 4.6 `ToolResult.fail(error, **meta)` —— 額外資訊走 meta 不走 data
`fail` 沒有 `data` 參數，寫 `data={...}` 會被塞進 `meta['data']`。

### 4.7 SQL 片段裡的 `%` 要寫 `%%`
會被塞進 `sqlalchemy.text()` 且該查詢帶參數時，單一個 `%` 會被 psycopg2 當佔位符炸掉。

### 4.8 測試不要靠現成資料
本地庫的班次會隨時間全部變成「已完成」，靠 `SELECT` 撈「準備」班次當測資
會在某天突然整支紅掉（2026-08-16 發生過）。自建 fixture + rollback。
注意 `session.rollback()` 會連 fixture 一起清掉，每個 case 之後要補回。

### 4.9 macOS 更新後 Postgres 起不來
重開機讓 `postmaster.pid` 殘留，而該 PID 被別的進程回收 → Postgres 保守拒絕啟動，
launchd 每 10 秒重試一次。修法（先確認 `pgrep -x postgres` 沒東西）：
```bash
rm /opt/homebrew/var/postgresql@16/postmaster.pid
```
