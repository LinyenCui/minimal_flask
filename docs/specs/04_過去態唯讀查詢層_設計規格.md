# 過去態唯讀受護欄查詢層 — 設計規格

> 狀態：設計草案，待使用者審核後實作 Phase 1
> 對象表：`completed_trips`（過去態，append-only 成品倉庫，無 R-5 時間鎖）
> 目標：用「AI 生查詢規格 → 護欄層編譯成安全 SQL」取代「每個查詢維度手焊一個參數」。
> 北極星對齊：[[project_ai_vision_layering]]「AI 生受護欄約束的 SQL 式操作，非封閉 atomic-tool 白名單」。

---

## 1. 為什麼（問題）

現況查詢 = 「白名單參數的笛卡兒積」：每多一種查法要在 schema / 函數簽名+WHERE / 各呼叫點三處手焊，且會漂移（aggregate 曾漏傳 fare_amount）。目前**仍無法表達**：
- GROUP BY 聚合：「各司機本週各加總多少」「按類別分組」
- 排序：「金額最高的 5 筆」「載最多次的客戶」
- 任意欄位組合 / 多值 IN

這層就是要讓上述變成「AI 生規格」，不再改程式。

## 2. 不是什麼（安全邊界，務必守住）

- **不是** text-to-SQL：AI **永不**產生 SQL 字串。AI 只產出「結構化查詢規格（JSON）」，由護欄層編譯。
- **只讀**：本層永不 INSERT/UPDATE/DELETE。mutation 維持現有 atomic tool（鎖 + reason + audit 不退讓）。
- **只過去態**：Phase 1 FROM 固定 `completed_trips`，AI 不能指定 table（三時間態選錯表最致命）。

## 3. 核心契約：查詢規格（AI 生成的 JSON）

```jsonc
{
  "filters": [                                  // 全部 AND
    {"col": "date",        "op": "between", "value": ["2026-06-07", "2026-06-13"]},
    {"col": "category",    "op": "=",       "value": "東洋"},
    {"col": "total_fare",  "op": ">",       "value": 1400}
  ],
  "group_by":   ["driver_id"],                  // 選填；給「各司機…」用
  "aggregates": [                               // group_by 或聚合查詢時用
    {"fn": "count"},
    {"fn": "sum", "col": "total_fare", "as": "金額"}
  ],
  "order_by":   [{"col": "金額", "dir": "desc"}],// 可排聚合別名或欄位
  "limit": 80
}
```

- 無 `group_by`/`aggregates` → 明細列表（回 CompletedTripView，沿用現有 carousel）。
- 有 `group_by`/`aggregates` → 分組統計（回新的通用統計 view）。

## 4. 欄位白名單（allowed_columns）

只有白名單內的欄位可被 AI 指定；其餘（含 PII）一律拒絕。每欄宣告：實體欄/虛擬謂語、型別、允許的 op、可否 group/sort。

| col（AI 用名） | 對應 | 型別 | 允許 op | group | sort |
|---|---|---|---|---|---|
| `date` | date | date | =, >=, <=, between | ✓ | ✓ |
| `driver_id` | driver_id | int | =, in | ✓ | ✓ |
| `category` | category（枚舉 診所/東洋/臨時） | enum | =, in | ✓ | ✓ |
| `total_fare` | **虛擬** `COALESCE(meter_fare,0)+COALESCE(extra_fare,0)` | int | =, !=, >, <, >=, <=, between | ✗ | ✓ |
| `has_fare` | **虛擬** `total_fare > 0` | bool | = | ✓ | ✗ |
| `customer` | **虛擬謂語** 起/終=值 OR via 拆 '+' 含值 | text | = | ✗ | ✗ |
| `location` | 起/途/終任一 ILIKE | text | ilike | ✗ | ✗ |
| `start_point` / `end_point` | 同名 | text | =, ilike | ✓ | ✓ |
| `passenger_name` | passenger_name | text | =, ilike | ✗ | ✗ |
| `is_leave` | **虛擬** `passenger_leave_reason IS NOT NULL` | bool | = | ✓ | ✗ |

聚合輸出欄（如別名「金額」）可被 `order_by` 引用。
**排除**：`completed_trips` 無電話/地址/生日，但仍明令只 SELECT 白名單欄（給聚合/明細 view 用的固定欄組），不讓 AI 自選投影。

## 5. 不可被 AI 覆寫的固定謂語 / 護欄

1. **表固定** `completed_trips`（過去態），AI 不能改 FROM。
2. **虛擬謂語**內建、AI 只填值：`total_fare`、`has_fare`（總額>0，剛修的語意）、`customer`（起/終+via 拆 '+'）、`is_leave`、`category` 枚舉值校驗。
3. **太陽週**：AI 仍先 call `sun_week_info` 拿日期（不變），規格只放 date 值 → 不讓 AI 自算週次。
4. **強制 LIMIT**：未給或超過上限一律夾到 80（Flex 50KB）；聚合結果列也夾上限。
5. **值一律 named param 綁定**（:p0, :p1…），AI 字串永不進 SQL 結構 → 注入面為零（沿用現有 83 處 text() 慣例）。
6. **型別 coerce**：值依該欄宣告型別 coerce（str→int/date），沿用 `_coerce_int` / UnifiedDateParser。
7. **第二道防線**：本層走 `SET TRANSACTION READ ONLY`（或獨立 readonly session），即使編譯出意外 mutation 也被 DB 擋。

## 6. 編譯流程

```
query_spec(JSON)
  → 驗證：每個 col ∈ allowed_columns？op ∈ 該欄 allowed_op？value 型別合法？group/sort 欄合法？
        （任一不過 → ToolResult.fail「不支援的查詢條件：…」，不默默忽略）
  → 編譯：每個 filter → 預寫好的 WHERE 片段 + bind param
          group_by/aggregates → SELECT 子句 + GROUP BY（皆白名單欄）
          order_by → ORDER BY（白名單欄/聚合別名）
          LIMIT 夾上限
  → readonly session 執行 → rows
  → 明細 → CompletedTripView[]；分組 → GroupedStatRow[]
```

## 7. 與現有 atomic tool 並存

- **Phase 1 新增一個 tool** `query_completed_trips_advanced(spec)`，掛進 completed_trip skill。
  - 簡單查詢仍可走既有 `query_completed_trips`（離散參數，向後相容、低風險）。
  - skill prompt 引導：要 GROUP BY / 排序 / 複雜範圍組合 → 用 advanced(spec)。
- **Phase 2**（驗證穩定後）：把離散參數的 query/aggregate 收斂進 advanced，縮短 tool 清單（解 ~25 tool 壓力）。
- mutation tool 完全不動。

## 8. 渲染

- 明細：複用 `render_completed_trip_list_carousel`（回傳形狀對齊 CompletedTripView，避免 agent `_render_result` 又長 isinstance 分支）。
- 分組統計：新增 `render_grouped_stat_card`（標題 + 每組一列：組鍵 → count / sum…）。聚合結果列數夾上限。

## 9. 分期 / 驗收

| Phase | 內容 | 驗收 |
|---|---|---|
| **1** | filter（含 total_fare 範圍）+ order_by + group_by 聚合；新 advanced tool；readonly session | 「各司機本週東洋加總」「金額最高 5 筆」「金額 1400~2000 的明細」**不用改程式**就能答 |
| 2 | 收斂舊 query/aggregate 進 advanced；縮 tool 清單 | tool 數下降、行為等價（回歸不退） |
| 3（未定） | 評估擴到現在態 `trips`（要處理 R-5 鎖 + 今天流動邊界 + 表路由） | 另開規格 |

## 10. 風險

- **最大風險不是注入**（named param 全綁），而是 **AI 把意圖映射錯欄/錯 op** → 靠白名單 + 欄位 description + 拒絕未知條件（不默默忽略）緩解。
- 大結果撐爆 Flex → 強制 LIMIT + truncated。
- 過度工程 → 嚴格圈在過去態查詢，不長成通用 ORM（[[feedback_dont_bloat_rewrite]]）。

## 11. 不做（YAGNI）

- 不支援 JOIN、子查詢、OR 群組（Phase 1 全 AND；真有需求再說）。
- 不讓 AI 自選 SELECT 投影欄（固定欄組給 view 用）。
- 不碰 mutation、不碰現在態/未來態。
