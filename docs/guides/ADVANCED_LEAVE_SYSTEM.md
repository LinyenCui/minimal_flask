# 🎭 高級請假系統：三層次障眼法機制指南

## 📖 核心理念

我們的請假系統設計了一個精妙的「三層次障眼法」機制，讓系統在滿足業務需求的同時，保持技術架構的簡潔和穩定。

> **核心思想**：請假不是真正的「停止」，而是「帶著標記繼續執行」

---

## 🎯 三層次請假架構

### 🎭 第一層：表面顯示（用戶看到的）
```
班次顯示：請假（原因）
狀態含義：用戶理解為「這個班次請假了」
操作體驗：符合直覺，清晰明確
```

### ⚙️ 第二層：系統實現（程式運行的）
```
trips.status：依然是「準備」
passenger_leave_reason：記錄請假原因
業務流程：正常執行所有步驟
```

### 🏭 第三層：生產線邏輯（自動化的）
```
自動完成：時間到達自動掉入completed_trips
車資調整：按用戶設定的加成計算
完整記錄：所有數據都會被正確保存
```

## 🎪 三種請假模式詳解

### 🚀 模式一：乘客臨時請假（現在態）

**適用場景**：已匯入到生產線上的班次，乘客臨時無法搭車

#### 🎬 障眼法機制
```sql
-- 用戶看到的
顯示狀態：請假（新建路乘客臨時有事）

-- 資料庫實際的
trips.status = '準備'  -- 骨子裡還是準備狀態！
trips.passenger_leave_reason = '新建路乘客臨時有事'
trips.extra_fare = -30  -- 直接設定為用戶輸入值
```

#### 🎯 操作命令
```bash
# 完整格式
乘客請假 139 -30 新建路乘客臨時有事

# 互動模式（推薦）
修改狀態 139 請假
# 然後輸入：新建路乘客臨時有事 -30
```

#### 💡 巧妙之處
- ✅ **業務連續性**：班次會正常執行完整流程
- ✅ **數據完整性**：自動掉入completed_trips，記錄完整
- ✅ **收費靈活性**：支援負數加成，反映請假損失
- ✅ **顯示友善性**：用戶看到的是直觀的請假狀態

---

### 🏗️ 模式二：固定班次長期請假（未來態）

**適用場景**：客戶長期無法搭車，需要在模板層級設定請假

#### 🎬 障眼法機制
```sql
-- 設定階段（在整備區域）
fixed_schedules.status = '請假'  -- 真的改狀態
fixed_schedules.note = '診所乘客長期住院'
fixed_schedules.surcharge = -50

-- 匯入階段（自動傳承到生產線）
trips.status = '準備'  -- 重點：依然是準備！
trips.passenger_leave_reason = '診所乘客長期住院'  -- 自動帶入
trips.extra_fare = -50  -- 自動帶入調整後的加成
```

#### 🎯 操作命令
```bash
# 設定長期請假
固定班次請假 5 -50 診所乘客長期住院

# 查看設定結果
固定班表 診所

# 恢復正常
固定班次恢復 5
```

#### 🚀 自動傳承機制
這是最精彩的部分！一旦設定了固定班次請假：

```python
# 匯入時的自動檢查邏輯
if fixed_status == '請假' and fixed_note:
    # 🎯 關鍵：自動將請假狀態帶到新班次
    passenger_leave_reason = fixed_note
    import_extra_fare = adjusted_surcharge
    status_counts['請假'] += 1
```

**效果**：
1. 設定一次長期請假
2. 後續所有週次匯入都自動帶上請假狀態
3. 無需每次匯入後重新設定
4. 真正實現「模板級別」的請假管理

---

### 🔄 模式三：請假狀態恢復（跨時間態）

**適用場景**：客戶恢復搭車，需要清除請假設定

#### 🎬 恢復機制詳解

**固定班次恢復**：
```sql
-- 清除模板請假設定
UPDATE fixed_schedules 
SET status = '準備', 
    note = NULL,
    surcharge = original_surcharge
WHERE id = 5
```

**生產線請假恢復**：
```sql
-- 檢查並清除現有班次的請假標記
UPDATE trips 
SET passenger_leave_reason = NULL,
    extra_fare = CASE 
        WHEN extra_fare < 0 THEN 0 
        ELSE extra_fare 
    END
WHERE fixed_trip_id = 5
```

#### 🎯 操作命令
```bash
# 恢復固定班次（影響未來匯入）
固定班次恢復 5

# 恢復當前班次（影響已匯入班次）
修改狀態 139 準備
```

## 🎨 設計哲學深度解析

### 🎭 為什麼要用「障眼法」？

#### 1. **業務邏輯簡化**
```
傳統做法：請假 = 複雜的狀態分支處理
障眼法：請假 = 正常流程 + 特殊標記
```

#### 2. **技術架構穩定**
```
狀態機複雜度：4種狀態 vs 20+種狀態組合
代碼維護性：統一流程 vs 到處都是if-else
```

#### 3. **數據完整性保證**
```
請假班次：依然會生成完整的completed_trips記錄
統計分析：數據不會因為請假而缺失
歷史追溯：所有操作都有完整記錄
```

#### 4. **用戶體驗優化**
```
視覺呈現：清晰的請假狀態標示
操作邏輯：符合直覺的請假概念  
功能完整：支援各種請假場景
```

### 🏭 生產線思維在請假中的體現

#### 產品標記系統
```
正常產品：無標記，正常流動
請假產品：帶有「請假標籤」，依然流動
取消產品：從生產線移除，不再流動
```

#### 品質控制流程
```
1. 整備區域：設定產品模板的請假屬性
2. 生產線區域：標記在線產品的請假狀態  
3. 成品倉庫：記錄所有產品的完整信息
```

#### 自動化傳承機制
```
模板請假 → 自動生成請假產品
模板恢復 → 後續產品恢復正常
歷史產品 → 保持原有狀態不變
```

## 💡 最佳實踐建議

### 🎯 請假設定策略

#### 短期請假（< 1週）
- ✅ 使用「乘客請假」模式
- ✅ 針對具體班次設定
- ✅ 保持固定班次模板不變

#### 長期請假（≥ 1週）
- ✅ 使用「固定班次請假」模式
- ✅ 在模板層級設定
- ✅ 享受自動傳承機制

#### 不確定期間
- ✅ 先設定固定班次請假
- ✅ 客戶恢復時立即恢復模板
- ✅ 避免影響後續匯入

### 🎨 加成設定技巧

#### 完全請假
```bash
加成設定：-100 或 -(原車資)
適用：客戶完全不搭車
```

#### 部分補償
```bash
加成設定：-30 到 -50
適用：客戶臨時有事，部分補償
```

#### 無損請假
```bash
加成設定：0
適用：提前通知的合理請假
```
