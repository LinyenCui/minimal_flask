# Gemini Prompt for Booking Information Extraction

**任務目標:**
嚴格分析以下來自使用者的【預約請求文字】，僅從文字中提取出結構化的預約資訊，並以純粹的 JSON 物件格式回傳。提取的資訊將用於後續的資料庫記錄。

**欄位定義:**

*   **必要欄位** (如果使用者文字中明確提到，必須提取，否則其值必須是 `null`，絕對不可猜測或生成範例):
    *   `date`: 預約日期。格式應為 YYYY-MM-DD (例如 "2025-05-04")。接受相對日期如 "今天", "明天", "後天", "星期X" (例如 "星期一")，請直接返回這些相對詞彙。
    *   `time`: 預約時間。格式應為 HH:MM (例如 "09:30", "14:00")。接受模糊時間如 "早上", "下午", "晚上" 或中文描述如 "下午三點半"，請直接返回這些詞彙。
    *   `start_point`: 出發地點 (字串)。例如 "高鐵站", "客戶家地址", "公司前門"。

*   **可選欄位** (如果使用者文字中明確提到則提取，否則其值必須是 `null`):
    *   `end_point`: 目的地 (字串)。例如 "成大醫院", "公司地址", "東洋", "客戶家"。
    *   `category`: 預約類別 (字串)。常見值為 "東洋", "診所"。如果未提及，應為 `null`。
    *   `via_point`: 途經點 (字串)。 指從起點到終點過程中，需要【中途停留】或【指定路線經過】的【地點名稱本身】。 **提取時請排除 \"經由\", \"經過\", \"先去\", \"再去\", \"繞去\" 等觸發詞。** 例如 "安平", "市政府", "郵局"。

**重要規則：**
1.  **只提取使用者文字中【明確存在】的資訊。**
2.  對於必要欄位 `date`, `time`, `start_point`，如果使用者文字中**沒有明確提供**，其值**必須**是 `null`。
3.  **絕對不要猜測、推斷或生成任何必要欄位的範例值。** 即使是很明顯的缺失（例如只有起點沒有終點），也不要填補。
4.  如果使用者輸入的資訊不足以填滿所有必要欄位，這是正常的，請將缺失欄位的值設為 `null`。
5.  輸出**必須**是**純粹的 JSON 物件**，不包含任何 ```json ``` 標記、說明文字、註解或其他非 JSON 內容。

**常見地點提示:**
*   "高鐵站" 通常指 台南高鐵站。
*   "東洋" 通常指 台灣東洋先端科技 (請直接提取 "東洋")。
*   "公司" 可能指用戶的公司，請提取如 "公司前門" 或用戶描述的原詞。
