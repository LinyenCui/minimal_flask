# 人性化對話設計原則

## 核心理念

**能一步到位的取決於用戶，意圖明確就直達，有疑慮就詢問。**

- 用戶輸入明確 → 直接執行，一步到位
- 用戶輸入模糊 → 逐層詢問，引導用戶表達真正意圖
- 每一輪對話都保留「退回重來」的機制

系統應該像一個有耐心的助手，根據用戶輸入的明確程度，決定是直接執行還是進一步詢問。

---

## 📌 明確 vs 模糊：決定對話深度

### ✅ 用戶輸入明確 → 一步到位

```
用戶: /12/13和緯四請假
         ↓
系統: 找到2個班次，進入請假模式
Quick Reply: [全部請假] [#846請假] [#844請假] [放棄]
```

用戶已經說了「請假」，意圖明確，直接進入請假模式的第二層。

### ⚠️ 用戶輸入模糊 → 逐層詢問

```
用戶: /12/13和緯四
         ↓
系統: 找到2個班次，請問您想做什麼？
Quick Reply: [🏥 請假] [🚫 註銷] [⚠️ 衝突] [🔍 查詢] [❌ 算了]
```

用戶只說了日期和地點，沒說要做什麼，需要先詢問。

---

## 📌 關鍵教訓：分層對話邏輯

### ❌ 錯誤做法

```
用戶輸入: /12/13和緯四
   ↓
系統直接顯示: [全部請假] [全部註銷] [全部衝突]
```

**問題**：
- 用戶可能只想操作其中一個班次，不是全部
- 用戶可能還沒決定要做什麼，只是先查詢
- 直接給「全部」選項是替用戶做決定

### ✅ 正確做法：分層遞進

```
第一層：問「要做什麼操作」
━━━━━━━━━━━━━━━━━━━━━━━━━━
用戶輸入: /12/13和緯四
系統: 找到2個班次，請問您想做什麼？
Quick Reply: [🏥 請假] [🚫 註銷] [⚠️ 衝突] [🔍 查詢] [❌ 算了]

             ↓ 用戶點擊「請假」

第二層：問「要操作哪些班次」
━━━━━━━━━━━━━━━━━━━━━━━━━━
系統: 以下班次可設定為請假，請選擇：
Quick Reply: [全部請假] [#846請假] [#844請假] [❌ 放棄]

             ↓ 用戶點擊「全部請假」或「#846請假」

第三層：執行操作
━━━━━━━━━━━━━━━━━━━━━━━━━━
- 全部請假 → 輸入「原因 加成」
- #846請假 → 單個班次請假流程
```

## 📌 設計原則

### 1. 每層只問一個問題

- 第一層：問「做什麼」（操作類型）
- 第二層：問「操作誰」（全部/單個）
- 第三層：問「怎麼做」（具體參數）

### 2. 給用戶退出選項

每一層都必須有「放棄」「取消」「算了」等選項，讓用戶隨時可以退出。

### 3. 保持上下文

使用 `pending_operation` 保存用戶的選擇上下文，這樣：
- 第二層可以知道第一層查到了哪些班次
- 第三層可以知道用戶選了哪個操作

### 4. Quick Reply 觸發文字要簡潔

```python
# ❌ 錯誤：帶日期地點的複雜字串
text=f"{date_str} {location} 請假"  # 發送 "12/13 和緯四 請假"

# ✅ 正確：簡潔的命令
text="選擇請假"  # 發送 "選擇請假"
```

## 📌 三時間態設計（重要！）

| 時間態 | 資料表 | 說明 |
|--------|--------|------|
| **過去態** | `completed_trips` | 日期 < 今天 |
| **現在態** | `trips` | 日期 >= 今天（今天 + **未來已匯入**的班次） |
| **未來態** | `fixed_schedules` | 模板，尚未匯入到生產線 |

**關鍵點**：12/13 已匯入到 `trips` 表 → 是**現在態**，不是未來態！

---

## 📌 狀態分類與對應選項

根據班次的實際狀態，提供不同的操作選項：

### 準備/待派狀態
```
Quick Reply: [🏥 請假] [🚫 註銷] [⚠️ 衝突] [🔍 查詢]
```

### 請假/註銷/衝突狀態
```
Quick Reply: [✅ 改回準備] [🔍 查詢]
```

### 混合狀態
```
Quick Reply: [📋 #ID詳情] [📋 #ID詳情] [🔍 查詢]
```

## 📌 實現檢查清單

實現對話功能時，確認以下事項：

- [ ] 是否分層遞進，而不是一步到位？
- [ ] 每層是否只問一個問題？
- [ ] 是否給用戶退出選項？
- [ ] 上下文是否正確保存和傳遞？
- [ ] Quick Reply 觸發文字是否簡潔？
- [ ] 時間態判斷是否正確？
- [ ] 是否根據班次狀態動態生成選項？

## 📌 退回重來機制

每一輪對話都必須保留讓用戶「退回重來」的選項：

```
任何階段都可以：
- 「放棄操作」→ 清除所有上下文，回到初始狀態
- 「取消操作」→ 同上
- 「算了」→ 同上
```

這確保用戶不會被「卡住」，隨時可以重新開始。

---

## 總結

> **人性化對話 = 明確就直達 + 模糊就詢問 + 隨時可退回**

```
判斷邏輯：
用戶輸入 → 意圖明確？
           ├─ 是 → 一步到位，直接執行或進入對應模式
           └─ 否 → 逐層詢問，引導用戶明確意圖
                    └─ 每層都保留「退回重來」選項
```

這個原則適用於所有需要用戶做選擇的場景，不僅限於請假/註銷/衝突功能。
