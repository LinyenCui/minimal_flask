# 數據庫結構變更記錄

## 日期：2025-03-14

### 關於 `week_number` 欄位的討論

1. **問題識別**
   - 發現 `trips` 表中的 `week_number` 欄位一直為空
   - 討論了該欄位的實際用途和必要性
   - 確認該欄位在 `completed_trips` 表中不存在

2. **分析**
   - `week_number` 欄位原本設計用於按週查詢和報表生成
   - 由於排程概覽每週更新，且只包含當前週的數據，該欄位實際上沒有被使用
   - `unique_code` 欄位已經包含了週數信息（格式為 `{fixed_trip_id}_{day_of_year}_{week_number}`）
   - 在代碼中，`week_number` 值是從日期計算得出的，而不是從數據庫讀取的

3. **決定**
   - 保留 `week_number` 欄位在數據庫結構中，避免破壞現有查詢
   - 在代碼中繼續計算和設置 `week_number` 值，確保數據完整性
   - 不再依賴該欄位進行查詢或報表生成
   - 未來可能考慮在數據庫重構時移除該欄位

### 關於 `unique_code` 初始化的決定

1. **問題識別**
   - 發現 `/initialize_unique_codes` 路由和相關函數已經完成其初始化工作
   - 這些代碼現在是冗餘的，可以被移除

2. **決定**
   - 不刪除這些代碼，而是保留作為參考
   - 在未來的代碼清理中可以考慮移除
   - 確保所有新添加的班次都會自動生成 `unique_code`

### 數據庫操作優化

1. **班次導入流程優化**
   - 修改了 `handle_import_fixed_trips_week` 函數，在導入新的固定班次前先清空班次概覽表
   - 確保在清空表前調用 `update_completed_trips()` 函數，將所有必要的班次移至已完成表
   - 這種同步操作避免了數據丟失的風險

2. **班次狀態管理**
   - 確認了狀態為 "準備" 的班次會被正確地移至已完成班次表
   - 這一過程通過多種機制保證，包括定時任務、應用啟動過程和手動函數觸發

### 代碼中的數據庫相關更改

1. **保留但不使用 `week_number`**
   - 在 `handle_import_fixed_trips_week` 函數中繼續計算和設置 `week_number` 值
   - 在 SQL 插入語句中保留 `week_number` 欄位
   - 在生成 `unique_code` 時繼續使用 `week_number` 值

2. **優化班次導入流程**
   - 修改了 `handle_import_fixed_trips_week` 函數，確保在導入新班次前先清空表
   - 添加了檢查，避免重複導入同一週的固定班次

### 未來計劃

1. **數據庫結構優化**
   - 考慮在未來的數據庫重構中移除冗餘欄位
   - 優化表結構，提高查詢效率

2. **代碼清理**
   - 移除不再需要的初始化代碼
   - 簡化與 `week_number` 相關的邏輯
